# 实施排期与关键决策

记录本项目从环境验证到端到端跑通的实施过程，以及过程中做出的关键技术决策。

## 架构速览

```
Chatflow: 开始 → 文档提取器 → 条件分支(IF/ELSE)
          ├─ 棋谱分析：工具(Stockfish MCP) → 整理引擎摘要 → LLM → 答复
          └─ 理论问答：知识检索(RagFlow 外部库) → LLM → 答复
```

Stockfish 经 FastMCP 注册为 MCP 工具（SSE）。

---

| 阶段 | 目标 | 验收标准 | 状态 |
|---|---|---|---|
| **D1** | 全链路环境验证 | Dify / RagFlow / Ollama 三服务可用，模型可调 | ✅ |

| **D7** | 输出质量打磨 | 报告与引擎数据一致、格式统一 | ✅ |

## 关键决策记录

### 1. 用「胜率损失」而非「厘兵差值」衡量着法质量

裸用 centipawn 差值会被将杀分数污染（mate → ±100000），且终局局面引擎不再搜索导致分数跳变。
改用 Lichess 胜率公式把评分映射到 0–100 的胜率区间，再计算某着法造成的胜率损失，天然有界、将杀安全。
阈值分类为 `best/exact / good / inaccuracy / mistake / blunder`。

### 2. Stockfish 用 MCP 封装，而不是自建 HTTP 接口

MCP 的工具带自描述 schema，宿主（Dify 等）能自动识别可调用工具，无需手写胶水层。
本项目用 FastMCP 暴露三个工具：`analyze_game`（整盘）、`best_moves`（单局面候选着法）、
`evaluate_position`（单局面评分）。

### 3. MCP 服务用单例长驻引擎

Stockfish 启动时要加载 NNUE 神经网络权重（约 125MiB），每次调用都重启引擎会非常慢。
`mcp_server.py` 保持一个长驻的 `SimpleEngine`，并把 `Threads` 设为 1、`Hash` 设为 64MB，
兼顾笔记本内存与并发下的稳定性。

### 4. 引擎数据先经代码节点汇总，再交给 LLM

原始逐着数据又长又冗余，直接喂给模型既费 token 又容易抓不住重点。
因此在 LLM 之前加一个「整理引擎摘要」代码节点，输出对局概要 + top 分歧点 + 改进建议素材，
LLM 节点的上下文只绑定这一份摘要。

### 5. 条件分支用「文本特征」而不是文件类型判断

Dify 文档提取器的白名单不含棋谱格式，直接上传 `.pgn` 会被拒绝。
改为让用户粘贴 PGN 文本，条件分支以输入是否含着法特征（如 `1. `）判断走哪个分支。

### 6. 知识库用 RagFlow 作为 Dify 的外部知识库

RagFlow 的文档解析、分块与检索能力更强，通过 Dify 的「外部知识库 API」接入后，
既保留了 RagFlow 的检索质量，又能让 Dify 工作流直接调用。
（同时也验证了 Dify 内置知识库链路，两者都可作为知识来源。）

### 7. ⭐ 模型选型：7B 级小模型不足以承担「严格遵循数据」的任务

**现象**：链路完全正确、引擎摘要准确，但本地 7B 模型输出的报告与数据严重不符
（编造回合数、不存在的着法）。

**结论**：这不是链路问题，而是模型能力问题——7B 级模型遵循「只能依据给定数据、禁止编造」
这类硬约束的能力弱，看到报告模板就习惯性自由发挥。

**决策**：把 LLM 节点切换到更强的托管模型（本项目最终使用 `Qwen/Qwen3.5-27B`），
并在提示词中硬性约束数据引用。切换后报告与引擎数据完全一致。

**认识**：在「以客观数据为准」的场景里，模型规模是硬门槛，不能靠调 prompt 完全弥补。

## 已知风险与对策

| 风险 | 对策 |
|---|---|
| RagFlow 内存占用高（Elasticsearch + MySQL + MinIO + Redis） | 按需启停；内存不足时改用 Dify 内置知识库 |
| 知识库内容变更后不生效 | 需重新发布应用 |
| 整盘分析耗时长（33 半回合 @ depth 16 约数分钟） | 调试时先用小 `--depth`；正式分析再调大 |
| 本地小模型输出不可靠 | 换用更大的托管模型（见决策 7） |
| 端口冲突（MCP 9000 被 MinIO 占用等） | 统一规划端口，MCP 使用 9002 |

更多具体问题见 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)。
